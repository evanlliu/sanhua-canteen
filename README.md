# sanhua-canteen — 员工食堂预约系统

> 当前版本：**V14.6（浏览器一员工绑定与管理员换设备激活）** · 单仓库、双分支、GitHub Pages + GitHub Contents API 直连。以后**只更新根目录 `README.md`**，不再创建 `README_V*.md` 等文件。本文件整合了 V1～V14.6 的功能和主要更新历史。

## 1. 项目结构与入口

- GitHub 仓库：`evanlliu/sanhua-canteen`
- `main` 分支：员工页 `index.html`、独立后台 `admin.html`、`config.js`、前端 JS/CSS、Token 混淆工具及本说明。
- `data` 分支：`data.json`，包含员工花名册、餐次配置和预约记录。
- 员工页：<https://evanlliu.github.io/sanhua-canteen/>
- 后台页：<https://evanlliu.github.io/sanhua-canteen/admin.html>
- 员工端**不提供后台入口**。静态网页无需 Cloudflare Worker，也不需要第二个仓库。

> **重要安全限制：** 公开仓库里的所有分支都可被读取；前端的 `tokenCiphertext` 与 `keyMaterial` 能一起还原 GitHub 写入 PAT，明文 `adminPassword` 也可被浏览器读取。GitHub Pages 无法提供可靠认证。**当前方案仅建议使用虚构资料作临时测试，不能用来保护真实员工隐私或生产凭据。** 使用真实花名册前请迁移到可安全保管令牌的服务端，并确保历史仓库提交未泄露数据。GitHub Token 的 Contents 写权限覆盖整个选定仓库，并非仅 `data` 分支。

## 2. 员工预约功能（V13 当前规则）

### 员工查找：工号或姓名均可模糊查询

在“**员工工号或姓名**”输入框输入一部分内容，下方自动出现员工下拉结果（工号 + 姓名），点选后会锁定对应的**唯一工号**用于预约，防止重名串号。

- 支持 `8`、`14`、`106`、`008` 等 **1～24 位工号**的完整、前缀、包含搜索；工号 `8` 和 `008` 保持区分。
- 支持中文姓名片段（如 `小明`）、西语/英语姓名片段（如 `CEPEDA`、`ORLANDO`）和多词查询（如 `CEPEDA ORLANDO`）；忽略英文字母大小写和常见拉丁重音符号。
- 工号精确匹配优先，其次工号前缀/包含，然后姓名精确/前缀/包含；最多展示 12 条。输入姓名时也显示工号，请核对后点选。
- “查看我的预约”区域为了准确识别仍然需要**完整数字工号**，不能只输入姓名。
- 手机端预约查询的工号输入框与上方员工搜索框使用一致的 **49px 高度、边框、圆角及内边距**，避免窄屏 Flex 布局压缩输入框。

### 餐次展示与预约时段（V11）

管理后台“餐次与时间设置”中的 **「对员工开放此餐次」** 是员工端**是否显示卡片**的唯一开关：

| 后台开关 | 当前食堂当地时间 | 员工端 | 能否预约 |
| --- | --- | --- | --- |
| 关闭 | 任意 | 不显示此餐次 | 否 |
| 开启 | 开始前 | 显示「尚未开始」，按钮「未到预约时间」置灰 | 否 |
| 开启 | 开始时间（含）至结束时间（不含） | 显示「开放预约」，绿色「立即预约」 | 是 |
| 开启 | 结束时间（含）之后 | 显示「今日已结束」，按钮置灰 | 否 |

示例：后台勾选“午餐 11:30–14:00”和“点心 17:30–20:00”，早上 `08:00` 两张卡片**都显示但都无法预约**；`11:30` 午餐开放，点心仍置灰；`14:00` 午餐结束仍显示；`17:30` 点心开放。后台关闭的餐次完全不出现。

> 此开关**不是**“预约开始时间”的单独配置；预约开放期严格采用后台餐次的开始～结束时间。目前没有“提前一天预约”或“开餐前提前预约”功能。

### 其他预约规则

- “用餐时间（当天）”只读展示 `yyyy-MM-dd HH:mm`，按后台配置的 IANA 时区（初始为 `America/Monterrey`）计算，约每 10 秒同步分钟和餐次状态。
- 只能预约食堂当地**当天**的餐次，不能编辑日期；提交时 GitHub API 再次确认是否在餐次时间内。
- 同一员工、同一天、同一餐次只能预约一次；**相互重叠时间段的不同餐次也不能重复预约**。不同不重叠时段可以分别预约。
- 成功时生成预约号码（例：`261020-B-0001`，即 2026-10-20 Plant B 的第 1 笔预约），可在下方凭**完整工号**查询历史记录。
- 员工首页没有大横幅/品牌页眉，右上角两个悬浮图标分别为三语言选择与“我的预约”跳转；进入页面自动聚焦员工搜索输入框。
- 首次打开页面默认跟随设备语言偏好，支持中文、English、Español (México) 手动切换。

## 3. 管理后台

`admin.html` 与员工端独立。当前后台功能：

- 管理员密码在 `config.js` 的 `adminPassword` 中配置，初始示例为 `1123`；打开登录页后自动聚焦密码框。
- 登录成功后 Cookie 保存**最多 5 小时**的前端登录状态，刷新不续期；退出登录清除 Cookie，过期后需要重新输入密码。
- 查看全量/今日预约统计、员工数量与启用餐次数量；可筛选工号/姓名/预约号、餐次和日期，删除预约并导出筛选结果 CSV。
- 从 `.xlsx` / `.xls` / CSV 导入员工花名册，表头应有 **工号** 与 **姓名**，支持合并更新、全量覆盖；重复工号不能共存。导入花名册不会自动删除预约历史。Excel 应把带前导零的工号列存为文本。
- 自定义最多 12 个餐次的 ID、中文/英文/西班牙语名称、起止时间、排序与“对员工开放此餐次”开关；可新增、编辑、停用或删除餐次。
- **从下拉框选择食堂时区**（默认 `America/Monterrey`），优先提供墨西哥常用时区，并支持其他浏览器内置 IANA 时区；不需要手动键入。切换时区并保存后，员工端的当天时间和餐次开放时段会按新时区计算。

管理后台口令是**前端显示门槛**，不是可靠的服务端权限验证。请勿将之用于生产系统的管理员鉴权。

## 4. 配置与部署

### `main/config.js`

只需要一个仓库 `sanhua-canteen`，`config.js` 在 `main` 分支根目录：

```js
window.APP_CONFIG = {
  github: {
    owner: 'evanlliu',
    repo: 'sanhua-canteen',
    branch: 'data',
    path: 'data.json',
    adminPassword: '1123',
    tokenCiphertext: '', // 本地 token-tool.html 生成
    keyMaterial: '',     // 本地 token-tool.html 生成
  }
};
```

不要把明文 PAT 发给其他人，不要把真实 PAT 放入公开仓库。`token-tool.html` 的混淆**不等于加密保密**：密文和密钥同时公开时任何访客均可能恢复 PAT。若仅本地测试，建议选用只限该仓库、短有效期、可随时撤销的测试凭据。**更新包中的 `config.js` 是空凭据模板，不要覆盖你现有的配置文件。**

### 发布到 GitHub Pages

1. 将网页文件上传至 `main` 分支根目录；`index.html` 需位于根目录。
2. 在同一仓库建立 `data` 分支，于根目录放置 `data.json`（已有分支和记录则保持不动）。
3. 在仓库 `Settings → Pages` 使用 `Deploy from a branch → main → /(root)`。
4. 发布后在浏览器使用 `Ctrl + F5` 强制刷新，或用隐身模式验证更新。
5. 演示访问可在员工端网址追加 `?demo=1`；演示模式仅使用本地浏览器数据，不会写入 GitHub。

**V13 已有 V12.2 仓库的最小更新：** 仅替换 `plant-schema.js`、`github-store.js`、`client-api.js` 与 `README.md`（共 4 个文件）。不要覆盖你已经配置的 `config.js`；已有 `data` 分支与预约记录无需手动改动，首次成功预约会自动保存 `sequenceCounters`。

## V12 — Plant 选择、完整花名册导入及预约号后缀

- 员工预约需选择 **Plant D / G / B / H** 中的一个；Plant 由员工手动选择，不依据部门字段自动推测。
- 预约提交、确认弹窗、预约结果、后台记录和 CSV 导出中都包含 Plant；旧预约记录仍可查询和删除。
- **V12 当时采用的号码规则，已被 V13 取代**：`C` + **10 位大写十六进制随机字符** + `-` + **一个 Plant 字母**（仅 `D` / `G` / `B` / `H`），例如 **`CEBA40FD604-D`**。编号由系统生成，员工不能手动编辑。
- 示例后缀：`CEBA40FD604-D`（Plant D）、`CEBA40FD604-G`（Plant G）、`CEBA40FD604-B`（Plant B）、`CEBA40FD604-H`（Plant H）。这些共享同一随机主体的编号仅用于格式演示，V12 每笔新预约曾使用独立随机主体。
- **兼容历史预约**：之前不带 Plant 后缀的编号（如 `CEBA40FD604`）继续支持查询和后台删除；V12 新预约必须带有效 Plant 后缀；V13 新预约则采用日期 + Plant + 流水号。Plant 是预约时员工选择的地点，与花名册中的部门、工厂或员工类型没有自动绑定关系。
- 后台新花名册导入时完整保留 **全部原始列名及对应列值**：`data.rosterColumns` 保存列名列表，`data.employees[].values` 保存按列顺序排列的完整信息，`employeeId` / `name` 仍供预约搜索。这样既保留 19 列，又避免在每名员工的数据中重复存储长字段名。
- 花名册后台增加“查看”完整信息和“导出完整花名册 CSV”。原有预约记录不会因全量覆盖员工名单而清除。
- 新版示例 Excel 共有 19 列、1441 人，其中 `ID` 与 `Name `（表头带一个末尾空格）分别映射到工号/姓名；所有其他列同样保留。Excel 的 `Hiring Date` 日期序列号会按 Excel 日期基准转为 ISO 日期（`yyyy-MM-dd`）方便查看。若合并更新的 Excel 表头与上次不同，请使用全量覆盖，避免列数据错位。
- 接口为避免 GitHub Contents API 读取超过 1MB 的文件，超过 800KB 会改为紧凑 JSON 序列化；超过 900KB 会提示备份归档。不包含真实员工花名册的任何内容，只有后台导入后才会保存到数据分支。
- **特别提醒：** 公开 GitHub 仓库的 `data` 分支可以被互联网用户读取。包含完整员工人事资料（尤其是成本中心、职位、部门）的花名册不应放入公开仓库。Token 混淆、前端登录密码及隐藏页面都不能提供可靠保密。

## V13 — 正式预约号改为日期 + Plant + 当日流水号

**当前生效规则（覆盖 V12 的随机预约号）：** `YYMMDD-Plant-NNNN`。

| 示例 | 含义 |
| --- | --- |
| `261020-B-0001` | 2026 年 10 月 20 日，Plant B 当天第 1 笔 |
| `261020-B-0002` | 同日 Plant B 第 2 笔 |
| `261020-D-0001` | 同日 Plant D 第 1 笔，独立从 0001 开始 |
| `261021-B-0001` | 2026 年 10 月 21 日，Plant B 重新从 0001 开始 |

- **日期**：以后台配置的食堂时区为准，从预约当天的 `yyyy-MM-dd` 取末两位年份、两位月份和两位日期。
- **Plant**：员工预约时选择 `D`、`G`、`B`、`H` 中一个。
- **当日流水号**：每个日期与每个 Plant 分开递增，范围 `0001`～`9999`，不按餐次重新编号。如果一天内同 Plant 有不同餐次，继续使用同一个流水序列。
- **删除不复用**：已分配的序号写入 `data.json` 的 `sequenceCounters`（以 `YYYY-MM-DD-Plant` 为键），删除预约后计数器不回退。
- **并发**：每次预约都在 GitHub Contents API 的读取→校验→更新事务内分配编号；发生 SHA `409`/匹配 SHA 的 `422` 冲突时重新读取并生成下一个序号，防止多人抢同一个编号。
- **兼容历史**：V12 的 `C1575A06F8C-B` 和更早不带后缀的随机编号仍可查询、筛选、导出、删除，不会自动重命名。
- **旧数据平滑升级**：无需重建 `data` 分支或手动加字段；新版首次成功预约时自动创建并保存 `sequenceCounters`。若某天已存在新样式号码但缺少计数器，也会从现存号码最大序号继续。
- **上限**：每个 Plant 每天最多分配 9999 个编号，超出会拒绝继续生成而不是重复编号。计数器持续存档，须关注 `data.json` 的体积。

**V13 最小更新**：`main` 分支覆盖 `plant-schema.js`、`github-store.js`、`client-api.js`、`README.md`。不替换 `config.js`，不手动修改 `data` 分支，建议部署完成后 Ctrl + F5 刷新两端网页。

## V14 — 电子备用餐票 / 现场滑动撕票（基础功能）

本版在 **GitHub Pages（`main`） + 同一仓库 `data` 分支的 `data.json`** 上实现轻量电子撕票，**没有增加 Worker 或服务端**。预计使用人数低于 50 人。后台默认关闭电子模式，餐票领用时间直接沿用餐次的开始、结束时间。

### 员工端

1. 仍按原有方式通过工号或姓名模糊搜索并选择 Plant、餐次；预约号仍是 `YYMMDD-Plant-NNNN`，如 `261021-B-0001`。
2. 新预约前，浏览器生成随机 **256-bit** 领餐凭据，把其 SHA-256 校验值和预约记录写入 `data.json`；原始凭据只存在当前浏览器的 `localStorage` 中。请求前先临时保存凭据，以便处理提交结果不明确的情况。
3. 顶部“我的预约”只展示**本机保存有效凭据**的餐票，**不再支持输入任何员工的工号查询他人预约**。这是普通页面的访问限制，不是员工身份认证；GitHub `data` 分支公开时，外部仍可查看原始数据文件。

### 明确的安全限制

**本方案不能达到真正的服务端安全核销。** 由于没有可信后端，GitHub Pages 上公开的 Token 混淆配置可被还原，公开 `data` 分支的原始预约信息也可直接访问。即使浏览器凭据只有本机持有，掌握写入权限的人仍可能修改预约和核销状态。工作人员也无法仅凭动态视觉效果完全识别伪造网页、录屏或实时转发。即使使用服务端提交确认，动态画面上秒数仍是基于提交时间戳加客户端计时的**参考时间**，并非独立可信的防伪时钟。

因此本版是**小规模临时备用、普通防截图/录屏辅助流程**，不是正式强身份认证或绝对防作弊系统；不应在公开数据仓库中放置真实敏感员工信息或长期有效写入 Token。没有工作人员独立电子核验时，仍必须要求工作人员现场看见滑动操作。异常领餐由管理员做记录并线下处理。

### V14.6 — 一浏览器一员工绑定 / 管理员设备转移（本次更新）

**目标：** 避免像 V14.5 那样，员工 A 的手机浏览器还能替员工 B 预约并保存两人的餐票。普通网页无法获取可信的物理硬件 ID、IMEI 或设备序列号，因此这里实现的是 **同一浏览器配置文件的持久随机标识绑定**，不是一台物理手机／电脑不可绕过的真实设备认证。**不要将其作为强制身份验证或可信防代领方案。**

#### 员工端规则

1. 首次打开员工页时，在当前浏览器的 `localStorage` 创建 256-bit 随机浏览器标识，保存到 `sanhua-canteen-browser-binding-v14.6`；演示模式使用独立的 `-demo` 后缀，避免污染正式浏览器绑定。对 GitHub 仅提交其 SHA-256 摘要（不提交本地随机标识明文）。
2. 新预约的 GitHub SHA 冲突重试事务中，检查 `deviceBindings`：**一个员工工号只对应一个浏览器摘要；一个摘要只绑定一个员工工号**。第一次成功预约自动绑定，以后相同员工可按原有餐次规则继续预约；不同员工／其他浏览器会拒绝提交。不因为简单删除预约记录就解除绑定。
3. 本机 `localStorage` 也保存已绑定工号；即使切换搜索结果，仍禁止替其他员工预约。查询旧电子票时，若验证结果显示本浏览器存在**两名及以上员工**的历史餐票，或者无法确认所有保存的票据是否属于同一员工，则暂时禁止新预约及待核销票操作，提示管理员处理，**不会直接删除、重置或恢复历史票据**。已使用状态和原有 8 秒领餐成功流程不变。
4. 每次查看和现场核销新版本餐票，须由当前浏览器提交设备摘要；不匹配或设备转移未完成的餐票无法使用原有核销流程。V14.5 没有绑定字段的历史票据保留兼容访问，但同一个旧浏览器中多员工混用的正常页面操作会受前述限制。
5. `deviceBindings` 保存在现有 `data` 分支的同一 `data.json`，以 **工号→设备摘要** 字典保存；新预约自身只增加 `deviceBound: true`，避免为每张票重复保存 64 位摘要。旧数据不需要手动迁移；第一次成功预约或管理员操作自动写入相应字段。保留花名册、预约号码、Plant、餐次、SHA 重试及电子核销凭据结构。

#### 管理员处理换设备

- **未使用餐票：** 后台「电子领餐管理」找到预约号，点「换设备重新签发」。系统重新签发随机领票密钥，同时将该员工绑定置为 `pending`，旧密钥即时失效，其他未使用餐票暂停核销；管理员核对工牌后，将生成的**一次性转移链接**当面交给新设备。员工在新浏览器打开 `#ticket=预约号.密钥`，通过 GitHub 校验新领票凭据后激活绑定并保存餐票。旧浏览器不能继续以原绑定核销，已用票不能重新签发。若同员工有其他未使用的旧票，需要逐张重新签发；后一张重新签发会使未激活的上一条链接失效。
- **没有可转移的未使用餐票 / 纯设备更换：** 后台新增加「员工设备绑定管理」，输入工号后点「重置设备绑定」。会将绑定置为 `pending`，生成**一次性浏览器激活链接** `#device=员工工号.密钥`；管理员当面交给新设备，在新浏览器打开完成激活，然后员工才可以按照预约时间重新预约。重置不删除旧餐票、不恢复已用餐票；之前未使用的旧餐票暂停核销，必须单独重新签发才能继续使用。没有激活链接不能在未完成转移期间抢占绑定。
- 两种一次性链接都不可公开、转发或保存到公开记录；页面解析后会从地址栏移除 Fragment。链接激活失败时需要管理员重新交付有效链接，已完成激活的链接不能再次转移绑定。
- 管理员操作仍采用当前静态网页前端密码，**不具备真实服务端管理员认证**，因此应人工核验员工工牌并防止公开链接泄露。

#### 数据字段、升级及风险

- `data.json` 根节点新增可选 `deviceBindings: { "员工工号": "64位SHA-256设备摘要 / pending" }`，管理员纯绑定重置时新增 `deviceResetTokens`（仅保存一次性密钥摘要，激活后删除）。重新签发的预约记录可能增加 `deviceTransferPending`、`deviceBindingSuspended` 等状态标识。这些字段均由代码自动维护，无需手改数据文件。
- **旧浏览器历史多员工票：** 例如截图所示员工 14 的已用票、员工 124 的待用票同时存在时，新版不会任选一个绑定；会阻止该浏览器新增预约及撕票，管理员应核验两人的身份，将待用票重新签发到其真正持有的设备。用于重新签发的链接须在**新设备**打开。已用票仍保留历史记录。
- **旧数据限制：** V14.5 没有记录浏览器标识，不能倒推历史上哪个物理设备属于哪个员工；新版只能根据本机已有凭据的服务端查询结果识别混用，并在首次新预约时创建服务端绑定。若历史凭据丢失，也无法自动恢复。
- **非强身份鉴权：** `localStorage` 可以被清空、复制；同一手机不同浏览器、隐私窗口会拥有不同标识。更重要的是，**公开的 `data.json` 暴露绑定摘要，客户端可伪造提交值；页面中的写入 Token 也可以被还原。** 因此具有技术能力的用户仍可能绕过限制。这是现场管理的业务约束，不是硬件级防作弊；需要强制保证时，必须迁移到安全服务器认证或受管设备体系。
- 建议先备份现有 `data` 分支 `data.json`，仅将本 ZIP 内容上传 `main` 分支并强制刷新员工与后台页面；**不需要手工修改/上传 `data.json`，也不要覆盖正式配置文件**。V14.6 测试没有接触生产数据；上线后请用测试员工和独立浏览器现场验证，并检查数据文件体积（GitHub Contents API 当前项目代码限制为 900KB）。
